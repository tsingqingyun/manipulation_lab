# 课堂部署验收

现有 BC、仿真、数据和依赖版本保持不变。本页分开核验教学链路、共享资源并发、教师材料和真实账号隔离。

## 一次固定协议验收

安装固定环境、下载已核验数据、准备可信教师模型后，从仓库根目录运行：

    CUDA_VISIBLE_DEVICES=0 scripts/lab_python.sh scripts/validate_classroom.py --output outputs/classroom_acceptance_v1

目录必须不存在。命令先运行教师参考的10个固定评测，再同时启动六个独立 Jupyter 内核工作进程；每组按顺序实际执行四个 Notebook。每组种子17、50轮、学习率1e-3/3e-4，每个模型标准5次及位移5次。总计12次学生训练、120个学生评测回合。重复相同初态只是并发功能验收，不增加独立统计样本数。

每类计算继续使用一个共享资源槽位；并发指六组同时提交并排队，不代表允许六个仿真任意争抢GPU。resource_events.jsonl 记录请求、获得和释放锁的单调时间。acceptance.json 报告最大活跃组数、每类槽位峰值、最大等待时间和进程RSS之和；后者包含共享页面，不能直接当作独占物理内存。

保留已执行的24份 Notebook、六组所有新结果和异常、class_selection.json、12行 class_results.csv、教师准备记录以及全部日志。任一真实训练/评测错误使验收失败；不自动重试、换种子或选更好分数。学生答案与第一次错误标注留空，报告是草稿，不能冒充完成作业。

## 教师参考与真实失败

`prepare_reference.py` 要求模型契约角色为 instructor_reference，数据哈希及固定环境匹配；重新执行原评测条件，核验实际失败视频能解码、逐步状态与动作数一致，输出 reference_manifest.json。各组通过 LAB_REFERENCE_ROOT 只读访问准备目录。若学生主模型全成功，Notebook 04 明确使用教师失败，报告继续保留学生自己的评测统计。

## 正式多账号部署的门槛

本机当前只有一个可用系统账号，不能创建六个系统账号；没有验收现有 JupyterHub 身份配置。脚本始终将 formal_multiuser_deployment_passed 和 account_isolation_verified 记为 false。六组内核全部通过也不能据此宣布六个学生账号已经安全部署。

管理员应在既有 JupyterHub / 独立系统用户部署上逐项实际核验：六个不同系统 UID；各组能执行自己的Notebook并写自己的输出；读取或写入其他组输出被拒绝；共享代码、数据及教师模型只能读取；所有组共享管理员持有的资源锁；内核进程继承正确 LAB_GROUP、LAB_OUTPUT_ROOT、LAB_REFERENCE_ROOT；六人登录和重新连接可用，并配置 CPU/RAM 限额。请保存每个账号的实际验证证据，不以只检查目录名称代替。

本项目没有创建新账号系统或更改现有服务。缺少管理员配置时，这一门槛保持未通过，其他已验证结果单独报告。
