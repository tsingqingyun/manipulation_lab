# Instructor Guide

The course uses four notebooks and a fixed two-learning-rate experiment. Preserve the existing PickPlaceCan task, official Can PH dataset, BC implementation and student architecture. Assess completed evidence and reasoning, not policy success-rate rankings.

## Before class

Follow [server setup](server_setup.md) to install from public resources, download/check the dataset, run the real smoke test, and generate the reference checkpoint and failure evidence. Reserve compute resources and prepare authenticated accounts, writable group notebooks/output roots and shared read-only data. Run the six-process acceptance on the intended server. Validate real account permissions and institutional access separately.

The reference model is generated by `prepare_reference.py --train`; no checkpoint is bundled in Git. Require `reference_manifest.json` with `ready: true` and watch its saved failure. Set `LAB_REFERENCE_ROOT` for all students. Its different existing architecture/seed are documented; never use its scores as student outcomes.

## Class sequence

| Stage | Teaching focus | Suggested time |
|---|---|---:|
| Demonstrations | Observations, actions, units, human playback versus policy rollout | 20 min |
| Controlled BC experiment | What is fixed; training/validation loss and checkpoint selection; only learning rate varies | 50–60 min |
| Evaluation | Matched cases, stable placement, initial-position coverage and Position Shift limits | 40–50 min |
| Failure discussion | Earliest observable error, frame/state timing, evidence versus hypothesis | 20–30 min |

The 2–3 hour target includes student exploration and discussion on a prepared server. Measure runtime and queue delays in advance. Notebook 02 trains both policies and executes all 20 cases; Notebook 03 reads these exact results. It does not launch a second evaluation. Avoid teaching students to rerun until success improves.

Students primarily edit their answers, selected demonstration/failure and keyframe/error control steps. Keep both learning rates, seed 17, 50 epochs, split and architecture fixed for the required assignment. Any optional extension must be separate and retain the mandatory results.

## Output isolation and restart behavior

Each assigned group (`group_01` through `group_06`) receives a unique timestamp/UUID session. Training, analysis and report stages are versioned. Notebook 01 starts a new session; Notebooks 02–04 reopen its current pointers. Students should rerun answer cells, not restart the entire assignment, when revising their report. Existing incomplete and unsuccessful runs remain on disk.

Group identifiers are not authentication. For real multi-user use, assign separate system accounts/JupyterHub users, student-writable notebook copies and output roots, read-only shared data/reference, and the common resource locks described in server setup. A notebook can execute arbitrary Python under its own account.

## Aggregate all groups

The authoritative schema is `CLASS_FIELDS` in `src/manipulation_lab/classroom.py`, also used by the blank [class_results.csv](class_results.csv) and exported student archives. There are **two rows per group run**, one per learning rate, including configuration, selected epoch, validation loss, checkpoint hash, both evaluation conditions and attributed failure notes. Missing or invalid runs remain explicit rows with blank metrics, not fabricated zeros.

Select each group's declared submission run, not its highest-scoring attempt. Create a JSON mapping the six group names to their chosen run paths, relative to the JSON file. For example, after `validate_classroom.py`, the generated `class_selection.json` already records exactly this selection:

```bash
scripts/lab_python.sh scripts/aggregate_results.py \
  --selection outputs/classroom_acceptance_v1/class_selection.json \
  --output outputs/classroom_acceptance_v1/teacher_review.csv
```

For an arbitrary number of explicitly selected run directories, use `--runs` followed by those paths instead of `--selection`. The selection mode requires all six groups and verifies group identity. Duplicate paths are rejected. A nonzero exit can accompany a CSV with invalid/incomplete rows; retain and inspect it. The output file must be new.

Student ZIPs include the same two-row CSV plus their evidence. For grading, extract submissions separately, inspect the report and original configurations, and use the selected original run directories when regenerating a classroom CSV. Local session-pointer paths in archives are provenance; do not assume they can resume another host's session without relocating them.

## Day-two discussion

Use the learning-rate comparison curves/table, paired standard/shifted cases, initial-position scatter, and the primary-policy success/failure videos. Display the checkpoint identity and role with each video. If no student success video exists, use an explicitly labeled reference success; if no primary student failure exists, use the prepared reference failure. Do not relabel recorded demonstration playback as a policy rollout.

Ask each group to show one frame at its first observable error and the corresponding requested-step state. Gripper width in meters must stay separate from the normalized command. Explain any nearest-frame offset. Invite an alternative explanation and a controlled test that could distinguish it. Compare the two rates without treating six same-seed group runs as independent evidence of algorithm superiority.

## Grading and unresolved cases

Use the [100-point rubric](assignment_student.md): 20 demonstration understanding, 25 training/experiment, 30 evaluation, 25 failure analysis/discussion. Generated report completeness only checks whether answer fields and an error marker are present; it does not grade correctness. Automated acceptance leaves human answers blank and reports DRAFT status deliberately.

Retain infrastructure failures and permit a documented rerun after fixing the cause. An unsuccessful manipulation with complete evidence is a valid result. If all available policies complete all cases without failure, preserve that outcome and supply a previously recorded, compatible, attributed real failure rather than searching new seeds for failure. Record any missing material as not prepared.

Current validation, including the difference between six concurrent processes and six authenticated users, is documented in [course_acceptance.md](course_acceptance.md). Historical acceptance records remain intact.
